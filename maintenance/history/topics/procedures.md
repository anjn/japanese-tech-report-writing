### B02：手順から推測できる説明

適用段階：両方。

出典：書くことと書かないこと、「書かない」の第2項。

> 手順から読者が推測できること

- 目的：操作を文章で読み上げ直すだけの説明を減らす。
- 採否案：条件付き採用。
- 理由：書き手には推測できても、想定読者には難しい場合がある。推測に任せると誤操作につながる情報もある。
- 修正案：想定読者にとって明らかな操作の言い換えは省く。操作の目的、選択条件、影響、成功判定など、理解や実行に必要な説明は、手順から推測できそうでも必要に応じて残す。

初回の合意は[第9回](../rounds.md#round-9)に記録。

<a id="l03"></a>

### L03：成功判定の参照

適用段階：両方。

出典：書き上げ後の重複の点検、第2項。

> 手順の「成功したときに見える出力」が、概要や根拠の節の数値と同じなら、数値を書かず「概要の表と同じ値になれば成功」と参照する。

- 目的：同じ値の重複と更新漏れを減らす。
- 採否案：修正して採用。
- 理由：操作中の節の往復は、見落としや照合の負担を増やす。更新漏れは値の整合確認で防ぐ。
- 修正案：成功判定に必要な値や状態は、操作の近くに示す。照合対象が大きい表などの場合は、確認する項目を明示して参照させる。再掲した値は元の値と一致させる。
- 例：「概要の表と同じなら成功」より、「出力件数が100件であることを確認します」のほうが、その場で判定できる。これは説明用の例であり、実測値ではない。

初回の合意は[第1回](../rounds.md#round-1)に記録。

<a id="l04"></a>

### L04：説明の短縮

適用段階：両方。

出典：手順書の書き方、冒頭段落。

> 説明の節は短いほど読みやすい。手順の節は、省くと再現できなくなる。説明は削り、手順は削らない。両者を同じ基準で簡潔にしない。

- 目的：簡潔にする過程で再現に必要な操作を落とさない。
- 採否案：修正して採用。
- 理由：操作の選択や失敗時の対応に必要な説明もある。手順にも不要な重複はあり、説明と手順の区分だけでは削除を判断できない。
- 修正案：作業に必要な操作、条件、確認方法を省略しない。説明も、目的の理解、操作の選択、誤操作の防止に必要な部分は残す。詳しい仕組みなど、その場で必要のない説明は別の節に分ける。

初回の合意は[第1回](../rounds.md#round-1)に記録。

<a id="p01"></a>

### P01：各手順の必須情報

適用段階：両方。

出典：手順書の書き方、四点の列挙。

> 各手順に、次の四点を書く。
>
> - 目的（この手順で何ができるか）
> - 実行する環境（どのマシン、どの仮想環境か）
> - コマンド（そのまま実行できる形で書く）
> - 成功したときに見える出力（期待する値、ファイル、表示）。値が違ったときに疑う点を、一文で添える。

- 目的：操作の目的、場所、内容、成否を迷わず判断できるようにする。
- 採否案：修正して採用。
- 理由：共通環境の毎回の再掲は不要。画面操作も対象に含め、失敗原因が不明なら推測で埋めない。
- 修正案：各手順で、目的、実行場所、操作、成功判定を確認できるようにする。共通事項はまとめて示し、切り替わる箇所で明記する。コマンドに限らず画面操作なども具体的に示す。失敗時の対応が必要なら、確認箇所や次の行動を示す。原因や出力を作り足さず、説明の長さを一文に固定しない。

初回の合意は[第5回](../rounds.md#round-5)に記録。

<a id="p02"></a>

### P02：前提と注意の位置

適用段階：両方。

出典：手順書の書き方、前提と注意の段落。

> 前提と注意は、それを使う手順の直前に書く。冒頭にまとめて並べると、読者は実行する時点で忘れる。

- 目的：実行時の見落としを防ぐ。
- 採否案：修正して採用。
- 理由：開始できるか判断するための環境や権限は、着手前に必要。操作直前の注意とは役割が異なる。
- 修正案：対象環境、必要な権限など、作業を開始できるか判断する前提は冒頭に示す。特定の操作に関する注意は直前に置く。影響が大きい注意は、冒頭で予告し、操作直前にも必要な範囲で再掲する。

初回の合意は[第5回](../rounds.md#round-5)に記録。

<a id="p03"></a>

### P03：ファイル配置のツリー

適用段階：両方。

出典：手順書の書き方、番号付き手順に続く第2項。

> 作業ディレクトリとファイルの配置は、最初にツリーで示す。

- 目的：実行場所とファイル間の位置関係を明確にする。
- 採否案：条件付き採用。
- 理由：複数のファイルの関係を示す場合には有効だが、一つのパスの指定で足りる場合もある。
- 修正案：作業ディレクトリと必要なパスを明示する。配置の関係を理解する必要がある場合は、関連する範囲のツリーを示す。作業前から必要なファイルと、手順で生成するファイルを区別する。

初回の合意は[第5回](../rounds.md#round-5)に記録。

<a id="p04"></a>

### P04：置換箇所と実行可能性

適用段階：両方。

出典：手順書の書き方、番号付き手順に続く第3項。

> コマンドは、変更が必要な部分（パス、名前）を、山括弧などで明示する。

- 目的：読者が変更する箇所を識別できるようにする。
- 採否案：修正して採用。
- 理由：プレースホルダーを含むコマンドは、そのまま実行できるとは限らない。P01の実行可能性と整合させる。
- 修正案：置換箇所を明示し、何に置き換えるかを実行前に説明する。置換が必要な例と、そのまま実行できる例を区別する。値が必要な入力は省略せず、秘密情報を記入例として実値で載せない。

初回の合意は[第5回](../rounds.md#round-5)に記録。

<a id="w05"></a>

### W05：操作の禁止を婉曲にすること

適用段階：両方。

出典：演出の抑制、第4項。

> 「〜してはならない」という命令調の断定より、「〜するわけにはいかない」のような、作業者の判断として書く形を選ぶ。

- 目的：過度に威圧的な語調を避ける。
- 採否案：修正して採用。
- 理由：禁止や停止条件を婉曲にすると、必須の制約か推奨かを判別しにくくなる。
- 修正案：必須事項、禁止事項、推奨事項を区別して書く。禁止や停止条件は「削除しないでください」など、取るべき行動が明確な表現にする。理由が判断に必要なら添える。威圧的な強調は避けるが、語調を和らげるために制約の強さを変えない。

初回の合意は[第6回](../rounds.md#round-6)に記録。

<a id="e05"></a>

### E05：事故や危険の列挙

適用段階：レビュー時。

出典：演出の抑制、第6項。

> 帰結の列挙によって事故や危険を煽らない。

- 目的：過剰な不安を与える演出を避ける。
- 採否案：採用。
- 理由：危険を煽る表現を避ける規範として残す。実際の影響や必要な注意を省く意味にはしない。
- 適用方針：判断や操作に必要な影響は、発生条件、対象、必要な対応とともに具体的に示す。根拠のない最悪の展開や、目的に関係しない危険を積み上げない。

初回の合意は[第8回](../rounds.md#round-8)に記録。

<a id="z03"></a>

### Z03：手順の番号と準備の区別

適用段階：両方。

出典：手順書の書き方。

> 手順には番号を付け、順序に依存することを示す。準備の手順と、本題の手順は、見出しなどで分ける。

- 採否案・適用方針：採用。順序のある操作には番号を付ける。準備と本題の区別は、読み手が作業の開始位置と前提を把握できるように示す。順序のない確認項目まで手順番号にしない。

初回の合意は[第19回](../rounds.md#round-19)に記録。
